分层全景：这些项目不在同一层

调研中最容易出错的地方是把"都叫多智能体"的项目摆在一张表里直接比分。飞书智能体与 Hermes 都不是 Multica 的替代方案——前者在业务应用层不碰代码仓库，后者是被 Multica 驱动的执行器。

Multica 推荐主线

Issue 看板 + Agent 身份 + Squad 路由 + 评审门禁。Go + Next.js + PG17，控制面与执行面分离，26 个 Agent CLI。

Vibe Kanban 同层竞品

本地优先看板，每任务独立 git worktree，内置 diff 评审。Apache 2.0，单机单人。

OpenHands Agent Canvas 同层竞品

自托管控制中心 + Agent Server + SDK。容器沙箱是一等公民，企业治理最完整（但在商业授权后）。

GitHub Agent HQ 闭源基线

Mission Control 跨仓库指派 Copilot / Claude / Codex，支持多 Agent 竞争同一 issue 择优合并。作为完备度参照。

L3 应用层 企业智能体搭建
面向业务角色 · 多渠道发布

飞书 aily 分工使用

闭源 SaaS。知识空间 + 连接器 + 可视化工作流，可操作飞书文档/多维表格/任务，支持定时主动工作。不碰代码仓库。

Coze Studio 能力补位

Apache 2.0，Go + React，全可视化拖拽。开源版不支持多租户/多空间。

Dify 能力补位

RAG + Workflow + 模型管理 + 观测一体。Workflow 可发布为 API / MCP Server，适合挂在 Agent 后面做知识服务。

L2 运行时层 单个 Agent 的循环
工具调用 · 记忆 · 技能 · 子代理

Hermes Agent 互补件

Nous Research 自进化 Agent 运行时。已是 Multica 内置的 26 个 CLI 之一。跨会话记忆 + 技能自改写 + 多执行后端（Docker/SSH/Modal/Daytona）+ ACP。

OpenClaw 范式参考

同样是 Multica 支持的 CLI。确定性 bindings 路由 + A2A 白名单 + 轮次上限；飞书实践的"确定性控制面"值得直接借鉴。

Claude Code / Codex / Cursor / 国产 CLI 执行器

Kimi、Qwen、Trae、DeepSeek Harness、华为云 CodeArts 等均在 Multica 支持列表内，换供应商是下拉框不是迁移。

L1 编排层 代码编织多 Agent
图 / 状态 / 断点恢复

LangGraph 补 D2 首选

有向图 + 类型化状态 + Postgres checkpointer + 原生 interrupt() HITL + 时间旅行调试。provider 无关、可内网。

CrewAI

角色制 Crew，上手最快；持久执行与 HITL 是短板，关键链路常需迁移。

AutoGen / MAF

AutoGen 已进入维护模式，新项目不建议采用。继任者 Microsoft Agent Framework 2026-04 GA，但生产护栏要走 Azure Foundry。

同一需求，不同实现路径

把"看起来都能做"拆成"具体怎么落、要自建什么、会卡在哪"。

场景 A · 需求单 → Agent 实现 → PR → 人工评审合入

方案具体落法需要自建优劣
Multica建 Issue → 指派 Agent → daemon 拉取 → 本地 CLI 执行 → 边做边评论 → 落 in_review → 人评审 → PR 合入触发 doneGit 凭据的隔离账号原生链路零开发；意图 / 执行 / 决策 / diff 挂在同一 Issue 下执行无沙箱；PR 由 CLI 自己开，Multica 不介入 PR 门禁
Vibe Kanban建卡 → 选 Agent → 自动开 worktree → 内置 diff 评审 → 合并团队协同的一切worktree 隔离干净，评审体验最好单机单人，无法团队化
OpenHandsCanvas 起会话或 automation 派单 → 容器沙箱执行 → 产出 PRIssue 层协同语义沙箱隔离；企业版有审计与预算无 Issue 看板心智，多人协作要自己贴
Hermes 单飞CLI 或网关触发 → local / Docker / SSH 后端执行Issue、指派、评审门禁全部自建记忆与技能最强等于自研一个 Multica
飞书 aily场景不成立 —— 不碰代码仓库，无 Git 集成、不产出 PR

场景 B · 多角色流水线（PM 拆解 → RD 实现 → QA 用例 → CR 复核） —— 本专项的靶心，分歧最大

方案具体落法确定性优劣
Multica Squad建 Squad（Leader + 前端/后端/测试 Agent）→ 指派 Issue → Leader 读 Roster 与 Instructions → 发一条 @ 评论派活 → 成员回帖 → Leader 被重新唤醒 → 决定下一步或推 in_review低LLM 生成评论零代码；人和 Agent 同队；有防自触发与去重无法强制阶段顺序；无 barrier、无断点续跑；Leader 每轮消耗一次模型调用
OpenClaw / 飞书范式声明式蓝图定义 teams + roleCatalog → 生成 agents/bindings → 控制面代码拆解并行分派 → 专家回交结构化 JSON → 按 publishOrder 顺序发布高代码保障顺序 / 状态 / 发布全可控；可灰度可回滚产物是消息文档不是 PR；无 Git 集成；三处配置联动易错
LangGraph四角色写成图节点，类型化状态流转，interrupt() 挂人工审批，Postgres checkpointer 持久化最高图+恢复可回放、可恢复、审批是一等公民纯代码无 UI；要自己接执行器与 Git
Multica + LangGraph
推荐		Multica 承载 Issue 与人机界面，把多阶段流程委托给 LangGraph 服务（作为特殊 Agent 或 MCP 工具暴露）高两边长处都拿到需自建集成层，是本方案工作量最大的一块

结论：Multica Squad 只能覆盖"路由"，覆盖不了"流程"。DFX 需求里若存在硬性阶段顺序或质量门禁（大概率存在），必须在 L1 层补确定性编排件。

场景 C · 定时巡检 / 质量报告

方案具体落法优劣
Multica Autopilotscron 配置，跑站会汇总、代码审计、报告生成原生无需开发；产物落在 Issue 里可追溯大批量仓库时受 runtime 数量限制，并发需压测
OpenHands automation独立 automation 组件负责调度、webhook、运行历史调度能力更强；容器后端便于横向扩报告落地位置要自己定
Hermes cron/cron 管理定时任务，复用同一 Agent 核心轻量单机视角，无团队级汇总
飞书 aily 定时任务定时主动工作，直接操作飞书文档 / 多维表格报告直接落到飞书表格，不可替代不能读代码仓库

结论：混合最优 —— 代码侧巡检用 Multica Autopilots 并经飞书渠道推送，报表维护用 aily 定时任务。

场景 D · 跨仓库大规模重构（同一改动 × N 个仓库）

方案可行性说明
Multica◐可批量建单批量指派，但没有"母任务 fan-out 到 N 仓再汇总"的原语；并发受 runtime 数量约束；失败重试是 Run 级不是批次级 —— 这是 Multica 的第二个能力缺口
Vibe Kanban○单机 worktree，规模上不去
OpenHands●Agent Server + 容器后端天然横向扩，automation 可编排批次
LangGraph 自建●fan-out / fan-in 是图的基本能力，失败重试与断点恢复原生
Agent HQ●Mission Control 支持跨仓库批量指派

场景 E · 飞书群内触发与进度同步

方案具体落法优劣
Multica Lark 渠道群内触发和跟进 Agent 工作官方维护（区别于社区维护的钉钉 / 企微 / Telegram）；与 Issue 时间线打通交互深度未知，需 POC 验证（能否群内看 diff、做审批）

选型建议与风险登记

一句话结论：Multica 是"人机混编任务协同层"里完成度最高、也最贴合国内工程团队习惯的开源方案，建议作为主线；但它不是编排引擎、也不提供沙箱，这两块必须从别处补。

推荐组合架构

触达层飞书群 / IM —— 触发任务、同步进展（Multica 的 Lark 渠道为官方维护）用开源
协同层Multica 自部署 —— Issue 看板、Agent 身份、Squad 路由、评审门禁、执行日志、token 归集用开源
编排层LangGraph 服务 —— 确定性阶段流程、人工审批节点、断点恢复（经 MCP 暴露给 Multica）自建
执行层Claude Code / Codex / Hermes / 国产 CLI —— 真正写代码的那一环用开源
隔离层专用 Unix 用户 + 容器 / VM —— Multica 明示不提供，必须自己加自建
治理层成本归集 / 预算熔断 / 效能指标 / 审计 —— Multica 只给原料，不给报表自建

为什么是 Multica

  • 为什么不是 OpenHands：本专项第一性需求是"人和 Agent 在同一套工程流程里协作"（D1）。Multica 在 D1 以及 D4 / D6 / D9 / D11 上的完成度是 OpenHands 开源版给不了的；OpenHands 强在 D3 / D7 / D8，但那些能力在商业授权闸门后——一旦付费，"开源方案"的评估前提就不成立了。
  • 为什么不自研：Multica 已解决的部分（26 个 CLI 的持续适配、daemon / runtime 模型、Issue-Run-Comment 数据模型、桌面与移动端、四种 Git 托管集成）自研成本极高且需长期投入，而这些都不是我们的差异化。工程投入应放在它明确不做的两件事上：隔离与确定性编排。

分阶段落地（按能力递进）

  • 阶段一 · 可用性验证：自部署 Multica（Compose，锁版本）+ 专用 Unix 用户隔离 + 接入两个 Agent CLI（一国际一国产）+ 打通一个自建 GitLab 仓库。验收：场景 A 端到端跑通，Issue 里能完整看到意图、执行日志、diff。
  • 阶段二 · 边界收敛：daemon 迁入容器，凭据收敛到 per-purpose deploy key，接通飞书渠道，上线首个 Autopilot 巡检。验收：一次刻意跑飞的 Run 无法读到容器外任何凭据。
  • 阶段三 · 编排补位：引入 LangGraph 编排服务，实现一条硬门禁流水线。验收：流程顺序在代码层被强制，不依赖 Prompt。
  • 阶段四 · 治理闭环：成本归集与预算告警、效能指标看板、批次调度器。验收：能回答"上月 DFX Agent 花了多少钱、采纳率多少、返工率多少"。

风险登记

高

R1 · License 不是标准 Apache 2.0

事实：LICENSE 为 Multica License = Apache 2.0 正文 + Part I 附加条款。禁止未获商业授权时向组织外第三方提供托管服务；禁止未获书面豁免时移除 UI 上的 Logo / 产品名 / 版权信息；条款 2.a 写明 producer 可单方把许可调整得更严格。多份第三方资料把它写成 MIT 或 Apache 2.0，是错的。

处置：内部单组织使用明确允许；白标进公司平台需书面申请 branding waiver。保留 fork，定期 review LICENSE 变更。

高

R2 · 官方明示不提供文件系统沙箱

事实：官方 Security model 原文 Multica makes no filesystem-sandbox guarantee；默认以 Codex danger-full-access / Claude Code bypassPermissions 运行，Run 继承 daemon 用户完整权限与 HOME，可读 SSH key、用云 CLI 凭据、无限制出网。每 Run 独立工作目录与 Run 级 Token 被官方定性为"降低爆炸半径的便利功能，不是安全边界"。

处置：按官方推荐由轻到重三选一：专用 multica Unix 用户 → 容器（只挂必需目录与 secret）→ VM。凭据用 per-purpose deploy key，daemon 用户 home 内不放任何生产凭据。

中高

R3 · Squad 是路由不是编排

事实：Leader 通过发一条 @ 提及的评论派活，成员回帖后被重新唤醒；没有 DAG、没有状态机、没有断点续跑。硬约束只能写进 Squad Instructions 里"劝"。

处置：L1 层补 LangGraph 编排；关键质量门禁放在 CI 而非 Agent 内。

中

R4 · 项目年轻，main 快速移动

事实：仓库 2026-01 创建，官方称"大部分工作日都发版"，1300+ open issues。

处置：锁定发版版本 + 镜像入内部仓 + 升级前回归 + 明确回滚预案。

中

R5 · 无 SSO、无预算熔断

处置：网关层做身份代理；在 LLM 网关（LiteLLM 或内部网关）层做成本硬约束。

中

R6 · 跨仓库批量能力缺失

处置：基于 Multica CLI / API 自建批次调度器，或把这类任务路由到独立流水线。

中

R7 · 国产 CLI 实际能力差距未知

处置：实测 Kimi / Qwen / Trae / CodeArts 与 Claude Code 的任务成功率差距，按任务类型分流 Agent。

低

R8 · 社区维护渠道质量不可控

事实：钉钉 / 企微 / Telegram 渠道为社区维护，仅 Slack 与 Lark 为官方维护。

处置：只用官方维护的 Lark 渠道，其余走自建 Webhook。
